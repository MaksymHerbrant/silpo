# Методика Health Score

## Чому не «власна формула з вагами на око»

Довільні ваги — перше, що розкритикує журі. Тому за основу взята **публічно відома
логіка профілювання поживності (nutrient profiling) у стилі Nutri-Score** (модель
FSA/Santé publique France): негативні бали за енергію, цукри, насичені жири й натрій,
позитивні — за клітковину й білок. Реалізація: [`backend/app/nutrition/score.py`](../backend/app/nutrition/score.py).

## Крок 1 — бали для товару (на 100 г)

Порогові таблиці такі самі, як у Nutri-Score; бал = кількість перевищених порогів.

| Компонент | Пороги | Діапазон |
|---|---|---|
| Енергія, кДж | 335, 670, …, 3350 | 0–10 |
| Цукри, г | 4.5, 9, 13.5, …, 45 | 0–10 |
| Насичені жири, г | 1, 2, …, 10 | 0–10 |
| Натрій, мг | 90, 180, …, 900 | 0–10 |
| Клітковина, г | 0.9, 1.9, 2.8, 3.7, 4.7 | 0–5 (позитивні) |
| Білок, г | 1.6, 3.2, 4.8, 6.4, 8.0 | 0–5 (позитивні) |

`Nutri-бал = негативні − позитивні`. Зберігається правило оригінальної методики: якщо
негативних балів ≥ 11, білок не зараховується.

Калорійність нормалізується: ккал × 4.184 → кДж. Якщо в даних прийшло значення > 1000
«ккал», воно трактується як кДж і переводиться назад. Сіль ↔ натрій: `сіль = натрій × 2.5 / 1000`.

## Крок 2 — кошик

Кошик зводиться до **середньозваженого по масі** профілю на 100 г:

```
маса позиції = вага упаковки × кількість   (якщо ваги немає — 300 г, консервативна оцінка)
профіль кошика[нутрієнт] = Σ(значення × маса) / Σ(маса)
```

Далі цей агрегований профіль проганяється через ту саму шкалу. Так один пакет цукерок не
«перебиває» три кілограми овочів, а великі за масою позиції справедливо важать більше.

## Крок 3 — шкала

```
score_0_100 = (40 − Nutri-бал) / (40 − (−15)) × 100     # обрізано в межах [−15; 40]
```

Клас: `A ≤ −1`, `B ≤ 2`, `C ≤ 10`, `D ≤ 18`, `E > 18`.

## Доданий цукор

MCP не розрізняє власні й додані цукри. Евристика: якщо у складі товару є маркер
(`цукор`, `сироп`, `глюкоза`, `фруктоза`, `патока`, `мальтодекстрин`, `меляса`, `мед`) —
увесь цукор товару вважається доданим; інакше — 0 (як у фруктах чи молоці). Якщо складу
немає, доданий цукор не нараховується. Це свідомо груба, але прозора оцінка.

## Відсутні дані

Товар без мінімального набору (енергія + цукор + хоча б один макронутрієнт) **не бере
участі в скорі**: він позначається `has_nutrition=false`, показується з бейджем «н/д», і в
UI видно покриття (`coverage.pct`). Нулі замість відсутніх полів не підставляються — це
спотворило б середньозважений профіль на користь «здорового».

Санітарна перевірка: будь-яке значення макронутрієнта поза `[0; 100]` г на 100 г
відкидається як помилка парсингу.

## Свідомі спрощення MVP

1. **Не враховуємо частку фруктів/овочів/горіхів** — MCP її не віддає. Через це рослинні
   продукти систематично недооцінені відносно оригінального Nutri-Score.
2. **Не розділяємо категорії** (напої, сири, жири мають у Nutri-Score власні шкали) —
   використовується загальна.
3. **Насичені жири** за відсутності даних оцінюються як 40% від загального жиру.
4. **Вага упаковки** за відсутності даних — 300 г.

## Що робить, а чого не робить LLM

Claude ([`backend/app/llm/explain.py`](../backend/app/llm/explain.py)) отримує **вже
обчислені** числа і лише формулює 2–3 речення українською. Системний промпт прямо
забороняє змінювати або перераховувати числа. Причини свопів формуються детерміновано з
різниці нутрієнтів. Якщо ключа Anthropic немає або запит впав — використовується
шаблонний текст, і сценарій не ламається.

## Дисклеймер користувачу

У відповіді API є поле `methodology`, яке фронтенд показує на головному екрані: це
спрощена евристика, натхненна відкритою методологією nutrient profiling, і вона **не є
медичною рекомендацією**.
